## Summary

**Q1: keeping a connection to a foreign handler current.** Of the six mods, only **Mekanism** keeps its pipe's connection state current from capability invalidation. Each transmitter holds one `BlockCapabilityCache` per side with an invalidation listener. The listener only marks the side dirty, and the network re-evaluates it on the next server tick. Mekanism also refreshes on `neighborChanged`. The connection state lives in the block entity and reaches the model as `ModelData`. **Pipez**, **Create**, and **Immersive Engineering** recompute arms only on neighbour block updates (`neighborChanged` or `updateShape`) and on load. They query the capability directly, or through a cache with no listener. From that code, an arm would go stale when a neighbour's capability changes with no block update; none of these mods has code that handles that case. Pipez and Create store arms as blockstate booleans. IE stores a connection byte in its block entity. **Modern Industrialization** stores explicit, player-made connections in its block entity and pipe-network nodes, with a SavedData holding the networks. A block connection is not dropped when the capability goes away: the transfer cache just returns nothing. **AE2** cables connect to grid nodes, not capabilities. Only AE2's parts (buses) hold capability caches with listeners.

NeoForge's rules, from source:

- Listeners are held by **weak reference**. The cache keeps its own listener strongly, so a cache lives as long as its owner keeps it, and is pruned once per level tick after it is garbage-collected.
- Listeners are keyed by the **target** position. They fire on `invalidateCapabilities(pos)`, and on chunk load and unload of the chunk that holds the **target**, not the owner.
- A cache only notifies while armed, and `getCapability()` re-arms it. Its listener must not call `getCapability()` and should not touch the level.
- `getCapability()` returns `null` for an unloaded target.
- Plain blocks without a block entity must call `invalidateCapabilities` themselves.

**Q2: wrench conventions.** NeoForge defines `c:tools/wrench` ([`Tags.Items.TOOLS_WRENCH`](https://github.com/neoforged/NeoForge/blob/4e35ebee793f48c39f5ddf20121eece88dc2aa0e/src/main/java/net/neoforged/neoforge/common/Tags.java#L988-L994)) and ships it empty. Mekanism, Pipez, MI, Create, and AE2 each add their own wrench to it. IE does not add its hammer (AE2 adds it optionally). These accept any item in the tag:

- Pipez, for side toggling.
- MI, for all wrench actions.
- Create, for `IWrenchable` blocks.
- AE2, for sneak-disassemble.
- Mekanism, for sneak-dismantle only. Mekanism's transmitter side cycling needs its own Configurator.

IE accepts only its hammer tag. The click conventions differ:

- **Pipez:** sneak-right-click toggles the arm under the cursor.
- **MI:** right-click on an arm cycles or removes it, right-click on the core adds an arm on the hit face, and sneak-right-click removes the pipe.
- **IE:** right-click with the hammer toggles the hit arm.
- **Mekanism:** sneak-right-click with the Configurator cycles NORMAL → PUSH → PULL → NONE. Sneak-right-click with a wrench dismantles.
- **Create and AE2:** no per-side disconnect. A Create wrench turns a fluid pipe into a glass pipe; sneak picks the block up.

All side-toggling mods choose the side by **hit position on the arm's shape**, falling back to the clicked face when the core is hit. In every mod, a manually disconnected side is **drawn the same as a side with nothing there**: no arm. The only extra cue is IE's: while the hammer is held, the selection outline shows disabled arms.

## NeoForge: `BlockCapabilityCache` and invalidation

Source files (NeoForge `26.1.x`, `4e35ebe`):

- **Cache lifetime and registration.** `BlockCapabilityCache.create(...)` calls `level.registerCapabilityListener(pos, cache.listener)` ([BlockCapabilityCache.java L59-L68](https://github.com/neoforged/NeoForge/blob/4e35ebee793f48c39f5ddf20121eece88dc2aa0e/src/main/java/net/neoforged/neoforge/capabilities/BlockCapabilityCache.java#L59-L68)). The class doc says: "Instances are automatically cleared by the garbage collector when they are no longer in use" ([L15-L21](https://github.com/neoforged/NeoForge/blob/4e35ebee793f48c39f5ddf20121eece88dc2aa0e/src/main/java/net/neoforged/neoforge/capabilities/BlockCapabilityCache.java#L15-L21)). The listener is a field of the cache ([L85](https://github.com/neoforged/NeoForge/blob/4e35ebee793f48c39f5ddf20121eece88dc2aa0e/src/main/java/net/neoforged/neoforge/capabilities/BlockCapabilityCache.java#L85)), so the cache object is what holds it strongly.
- **Weak references.** `ICapabilityInvalidationListener`'s doc says the listener "will be held by a weak reference, so it is important to keep a strong reference to it as long as you need it" ([ICapabilityInvalidationListener.java L10-L17](https://github.com/neoforged/NeoForge/blob/4e35ebee793f48c39f5ddf20121eece88dc2aa0e/src/main/java/net/neoforged/neoforge/capabilities/ICapabilityInvalidationListener.java#L10-L17)). `CapabilityListenerHolder` stores `ListenerReference extends WeakReference` in a map from chunk to block position to a set of references ([CapabilityListenerHolder.java L40-L50, L112-L137](https://github.com/neoforged/NeoForge/blob/4e35ebee793f48c39f5ddf20121eece88dc2aa0e/src/main/java/net/neoforged/neoforge/capabilities/CapabilityListenerHolder.java#L40-L50)). Cleared references are pruned by `clean()` ([L85-L110](https://github.com/neoforged/NeoForge/blob/4e35ebee793f48c39f5ddf20121eece88dc2aa0e/src/main/java/net/neoforged/neoforge/capabilities/CapabilityListenerHolder.java#L85-L110)). `clean()` runs from `LevelTickEvent.Post` ([CapabilityHooks.java L224-L228](https://github.com/neoforged/NeoForge/blob/4e35ebee793f48c39f5ddf20121eece88dc2aa0e/src/main/java/net/neoforged/neoforge/capabilities/CapabilityHooks.java#L224-L228), registered in [NeoForgeMod.java L593-L595](https://github.com/neoforged/NeoForge/blob/4e35ebee793f48c39f5ddf20121eece88dc2aa0e/src/main/java/net/neoforged/neoforge/common/NeoForgeMod.java#L593-L595)). A listener is also dropped when its `onInvalidate()` returns `false` ([L75-L80](https://github.com/neoforged/NeoForge/blob/4e35ebee793f48c39f5ddf20121eece88dc2aa0e/src/main/java/net/neoforged/neoforge/capabilities/CapabilityListenerHolder.java#L75-L80)). For a cache, that happens when its `isValid` supplier returns `false` at the moment of an invalidation ([BlockCapabilityCache.java L93-L116](https://github.com/neoforged/NeoForge/blob/4e35ebee793f48c39f5ddf20121eece88dc2aa0e/src/main/java/net/neoforged/neoforge/capabilities/BlockCapabilityCache.java#L93-L116)). Neither the docs nor the source has an explicit unregister call. The docs say: "there is no need to unregister it" ([docs, Block capability caching](https://docs.neoforged.net/docs/inventories/capabilities#block-capability-caching); [source md L168-L229](https://github.com/neoforged/Documentation/blob/89528c36e4eb34d46b1de346c045172ce8ca9fde/docs/inventories/capabilities.md#L168-L229)).
- **Where it lives.** The holder is a field on `ServerLevel`. `invalidateCapabilities(BlockPos)` calls `invalidatePos`, `invalidateCapabilities(ChunkPos)` calls `invalidateChunk`, and `registerCapabilityListener` calls `addListener` ([ServerLevel.java.patch L312-L339](https://github.com/neoforged/NeoForge/blob/4e35ebee793f48c39f5ddf20121eece88dc2aa0e/patches/net/minecraft/server/level/ServerLevel.java.patch#L312-L339)). On other levels, `Level.invalidateCapabilities` is a no-op ([ILevelExtension.java L117-L136](https://github.com/neoforged/NeoForge/blob/4e35ebee793f48c39f5ddf20121eece88dc2aa0e/src/main/java/net/neoforged/neoforge/common/extensions/ILevelExtension.java#L117-L136)). The cache factory takes a `ServerLevel`.
- **When listeners fire.** Listeners are keyed by the target `pos` passed to `create` ([CapabilityListenerHolder.java L40-L50](https://github.com/neoforged/NeoForge/blob/4e35ebee793f48c39f5ddf20121eece88dc2aa0e/src/main/java/net/neoforged/neoforge/capabilities/CapabilityListenerHolder.java#L40-L50)). They fire on:
  - `level.invalidateCapabilities(target)`;
  - **chunk load and chunk unload of the target's chunk.** `CapabilityHooks.invalidateCapsOnChunkLoad` and `invalidateCapsOnChunkUnload` call `invalidateCapabilities(chunkPos)` ([CapabilityHooks.java L212-L222](https://github.com/neoforged/NeoForge/blob/4e35ebee793f48c39f5ddf20121eece88dc2aa0e/src/main/java/net/neoforged/neoforge/capabilities/CapabilityHooks.java#L212-L222)). `ChunkEvent.Unload` is posted in `ChunkMap` after the chunk is saved and before `level.unload(levelChunk)` ([ChunkMap.java.patch L13-L17](https://github.com/neoforged/NeoForge/blob/4e35ebee793f48c39f5ddf20121eece88dc2aa0e/patches/net/minecraft/server/level/ChunkMap.java.patch#L13-L17)). `ChunkEvent.Load` is posted from `ChunkStatusTasks` ([ChunkStatusTasks.java.patch L19](https://github.com/neoforged/NeoForge/blob/4e35ebee793f48c39f5ddf20121eece88dc2aa0e/patches/net/minecraft/world/level/chunk/status/ChunkStatusTasks.java.patch#L19));
  - block entity `setRemoved()` and `clearRemoved()` at the target ([BlockEntity.java.patch L57-L67](https://github.com/neoforged/NeoForge/blob/4e35ebee793f48c39f5ddf20121eece88dc2aa0e/patches/net/minecraft/world/level/block/entity/BlockEntity.java.patch#L57-L67)). This covers placement, removal and chunk unload of a block entity, since `LevelChunk` calls `setRemoved` on its block entities when it unloads ([LevelChunk.java.patch L102-L103](https://github.com/neoforged/NeoForge/blob/4e35ebee793f48c39f5ddf20121eece88dc2aa0e/patches/net/minecraft/world/level/chunk/LevelChunk.java.patch#L102-L103)).

  The owner's own chunk loading or unloading does **not** fire anything for the owner. An internal comment notes that caches are **not** invalidated when a whole level unloads and chunk unload events do not fire ([CapabilityListenerHolder.java L21-L22](https://github.com/neoforged/NeoForge/blob/4e35ebee793f48c39f5ddf20121eece88dc2aa0e/src/main/java/net/neoforged/neoforge/capabilities/CapabilityListenerHolder.java#L21-L22)).
- **Who must invalidate.** NeoForge invalidates on chunk load and unload, and on block entity load, unload, placement and destruction. "In ALL other cases, it is the responsibility of the modder". For example, a plain block that provides a capability must invalidate in `onPlace` and in `affectNeighborsAfterRemoval` ([IBlockCapabilityProvider.java L17-L35](https://github.com/neoforged/NeoForge/blob/4e35ebee793f48c39f5ddf20121eece88dc2aa0e/src/main/java/net/neoforged/neoforge/capabilities/IBlockCapabilityProvider.java#L17-L35); [docs, Block capability invalidation](https://docs.neoforged.net/docs/inventories/capabilities#block-capability-invalidation)). A neighbour block update is **not** a capability invalidation, and the reverse also holds: `invalidateCapabilities` sends no block update.
- **Listener contract** ([BlockCapabilityCache.java L35-L58](https://github.com/neoforged/NeoForge/blob/4e35ebee793f48c39f5ddf20121eece88dc2aa0e/src/main/java/net/neoforged/neoforge/capabilities/BlockCapabilityCache.java#L35-L58)):
  1. Do not call `getCapability()` from the listener; it throws `IllegalStateException` ([L137-L139](https://github.com/neoforged/NeoForge/blob/4e35ebee793f48c39f5ddf20121eece88dc2aa0e/src/main/java/net/neoforged/neoforge/capabilities/BlockCapabilityCache.java#L131-L153)). "You should wait for some time (e.g. until your own tick)".
  2. "In general, do not perform any level access for the listener. The listener itself might be in a chunk that is being unloaded".
  3. "The listener does not receive notifications before `getCapability()` is called. After each invalidation, `getCapability()` must be called again to enable further notifications." The `cacheValid` flag gates this ([L80, L93-L97](https://github.com/neoforged/NeoForge/blob/4e35ebee793f48c39f5ddf20121eece88dc2aa0e/src/main/java/net/neoforged/neoforge/capabilities/BlockCapabilityCache.java#L93-L97)). A cache that is never queried never notifies. While it is disarmed, an invalidation still evaluates `isValid` to decide removal ([L94-L96](https://github.com/neoforged/NeoForge/blob/4e35ebee793f48c39f5ddf20121eece88dc2aa0e/src/main/java/net/neoforged/neoforge/capabilities/BlockCapabilityCache.java#L93-L97)).
  4. `isValid` is "a function to check if the listener still wants to receive notifications"; the docs suggest `() -> !this.isRemoved()` for a block entity.
- **Unloaded target.** `getCapability()` returns `null` when `!level.isLoaded(pos)`, with the comment "The cache will be invalidated when the chunk is loaded" ([L141-L150](https://github.com/neoforged/NeoForge/blob/4e35ebee793f48c39f5ddf20121eece88dc2aa0e/src/main/java/net/neoforged/neoforge/capabilities/BlockCapabilityCache.java#L131-L153)). Querying still re-arms the cache, so the later chunk load notifies.

## Per-mod findings

### Mekanism (`1.21.x`)

**Connection state.** The transmitter's block entity holds per-side `ConnectionType` (`NORMAL`, `PUSH`, `PULL`, `NONE`), set by the player, and computed bitmasks `currentTransmitterConnections` and `currentAcceptorConnections`. The type is in [ConnectionType.java L21-L24](https://github.com/mekanism/Mekanism/blob/bcd7a8bf594cff9614eb12238fe3776f19da24d9/src/main/java/mekanism/common/lib/transmitter/ConnectionType.java#L21-L24); the fields are in [Transmitter.java L73-L76](https://github.com/mekanism/Mekanism/blob/bcd7a8bf594cff9614eb12238fe3776f19da24d9/src/main/java/mekanism/common/content/network/transmitter/Transmitter.java#L73-L76). Rendering reads `getConnectionType(side)` into `ModelData` ([TileEntityTransmitter.java L304-L315](https://github.com/mekanism/Mekanism/blob/bcd7a8bf594cff9614eb12238fe3776f19da24d9/src/main/java/mekanism/common/tile/transmitter/TileEntityTransmitter.java#L304-L315)).

**Capability tracking.** `AbstractAcceptorCache` creates one `BlockCapabilityCache` per side. The same `RefreshListener` serves as both `isValid` and the invalidation listener ([AcceptorCache.java L25](https://github.com/mekanism/Mekanism/blob/bcd7a8bf594cff9614eb12238fe3776f19da24d9/src/main/java/mekanism/common/lib/transmitter/acceptor/AcceptorCache.java#L25); [AbstractAcceptorCache.java L32-L41](https://github.com/mekanism/Mekanism/blob/bcd7a8bf594cff9614eb12238fe3776f19da24d9/src/main/java/mekanism/common/lib/transmitter/acceptor/AbstractAcceptorCache.java#L32-L41)). The listener:

- holds the tile through a `WeakReference`, "so that if it gets unloaded it can be released from memory instead of being referenced by the listener still in the tile in a neighboring chunk";
- reports itself invalid once the tile is collected;
- on invalidation, only calls `transmitter.markDirtyAcceptor(side)` "so we don't evaluate the changed block until the server tick so that blocks hopefully had a chance to figure out their caps".

It skips the work while the transmitter is not valid. The source names the case of "the chunk the transmitter is in becomes inaccessible BUT is still loaded" ([AbstractAcceptorCache.java L94-L142](https://github.com/mekanism/Mekanism/blob/bcd7a8bf594cff9614eb12238fe3776f19da24d9/src/main/java/mekanism/common/lib/transmitter/acceptor/AbstractAcceptorCache.java#L94-L142)). Dirty sides are queued per network ([NetworkAcceptorCache.java L64-L80](https://github.com/mekanism/Mekanism/blob/bcd7a8bf594cff9614eb12238fe3776f19da24d9/src/main/java/mekanism/common/lib/transmitter/acceptor/NetworkAcceptorCache.java#L64-L80)). They are committed in `ServerTickEvent.Post` ([TransmitterNetworkRegistry.java L123-L133](https://github.com/mekanism/Mekanism/blob/bcd7a8bf594cff9614eb12238fe3776f19da24d9/src/main/java/mekanism/common/lib/transmitter/TransmitterNetworkRegistry.java#L123-L133)), where `refreshAcceptorConnections(side)` re-queries the side and sends an update packet if the bit changed ([Transmitter.java L593-L602](https://github.com/mekanism/Mekanism/blob/bcd7a8bf594cff9614eb12238fe3776f19da24d9/src/main/java/mekanism/common/content/network/transmitter/Transmitter.java#L593-L602)).

**Block updates as well.** `BlockTransmitter.neighborChanged` calls `refreshConnections(side)` ([BlockTransmitter.java L67-L75](https://github.com/mekanism/Mekanism/blob/bcd7a8bf594cff9614eb12238fe3776f19da24d9/src/main/java/mekanism/common/block/transmitter/BlockTransmitter.java#L67-L75); [Transmitter.java L669-L680](https://github.com/mekanism/Mekanism/blob/bcd7a8bf594cff9614eb12238fe3776f19da24d9/src/main/java/mekanism/common/content/network/transmitter/Transmitter.java#L669-L680)), with a `TODO` doubting this is the best way.

**Unloaded neighbour.** When computing acceptor connections, a side whose neighbour position is not loaded is skipped (`setForceUpdate`), not counted as disconnected ([Transmitter.java L343-L366](https://github.com/mekanism/Mekanism/blob/bcd7a8bf594cff9614eb12238fe3776f19da24d9/src/main/java/mekanism/common/content/network/transmitter/Transmitter.java#L343-L366)). Mekanism also tracks chunk ticket-level changes to treat "inaccessible" chunks as unloaded ([TransmitterNetworkRegistry.java L136-L164](https://github.com/mekanism/Mekanism/blob/bcd7a8bf594cff9614eb12238fe3776f19da24d9/src/main/java/mekanism/common/lib/transmitter/TransmitterNetworkRegistry.java#L136-L164); [TileEntityTransmitter.java L205-L214](https://github.com/mekanism/Mekanism/blob/bcd7a8bf594cff9614eb12238fe3776f19da24d9/src/main/java/mekanism/common/tile/transmitter/TileEntityTransmitter.java#L205-L214)).

**Clicks.**

- **Configurator, sneak-right-click.** With the Configurator in a "configurate" mode, sneak-right-click calls `IConfigurable.onSneakRightClick` ([ItemConfigurator.java L119-L160](https://github.com/mekanism/Mekanism/blob/bcd7a8bf594cff9614eb12238fe3776f19da24d9/src/main/java/mekanism/common/item/ItemConfigurator.java#L119-L160)). - **How the side is chosen.** `getSideLookingAt` ray-traces the per-arm collision boxes of the currently connected arms. If the player hits the centre, the clicked face is used ([L226-L242](https://github.com/mekanism/Mekanism/blob/bcd7a8bf594cff9614eb12238fe3776f19da24d9/src/main/java/mekanism/common/tile/transmitter/TileEntityTransmitter.java#L226-L242)).
- **Configurator, plain right-click.** On a transmitter this toggles redstone sensitivity ([Transmitter.java L714-L722](https://github.com/mekanism/Mekanism/blob/bcd7a8bf594cff9614eb12238fe3776f19da24d9/src/main/java/mekanism/common/content/network/transmitter/Transmitter.java#L714-L722)).
- **Wrench, sneak-right-click.** With any item that passes `MekanismUtils.canUseAsWrench`, this dismantles the block ([BlockBase.java L136](https://github.com/mekanism/Mekanism/blob/bcd7a8bf594cff9614eb12238fe3776f19da24d9/src/main/java/mekanism/common/block/prefab/BlockBase.java#L134-L140); [MekanismUtils.java L577-L590](https://github.com/mekanism/Mekanism/blob/bcd7a8bf594cff9614eb12238fe3776f19da24d9/src/main/java/mekanism/common/util/MekanismUtils.java#L577-L590)). Such items have `WRENCH_DISMANTLE` or are in `mekanism:configurators`, which includes `#c:tools/wrench`.

**Wrench tag.** Mekanism adds its Configurator to `c:tools/wrench` and pulls the whole tag into `mekanism:configurators` ([MekanismTagProvider.java L317-L320](https://github.com/mekanism/Mekanism/blob/bcd7a8bf594cff9614eb12238fe3776f19da24d9/src/datagen/main/java/mekanism/common/tag/MekanismTagProvider.java#L317-L320)). **Closed-side visuals.** A side set to `NONE` and a side with nothing there both report `ConnectionType.NONE` to the model and the shape ([Transmitter.java L53-L61](https://github.com/mekanism/Mekanism/blob/bcd7a8bf594cff9614eb12238fe3776f19da24d9/src/main/java/mekanism/common/content/network/transmitter/Transmitter.java#L53-L61); [TileEntityTransmitter.java L284-L300](https://github.com/mekanism/Mekanism/blob/bcd7a8bf594cff9614eb12238fe3776f19da24d9/src/main/java/mekanism/common/tile/transmitter/TileEntityTransmitter.java#L284-L300)). ### Pipez (`1.21.1`)

## Implications for #9 and #11

These are factual bearings, not decisions.

- **Who owns the cache (#11).** `BlockCapabilityCache` is held weakly by the level, so a `FluidSegments`-owned cache stays registered only as long as `FluidSegments` keeps it in a field or map. When `FluidSegments` drops it, for example when a pipe is removed or a side is wrenched off, the cache is pruned after GC; no unregister call is needed. The `isValid` supplier can retire a cache early. Its natural test for a block-entity-less pipe is "the node is still in `FluidSegments` and the side is still open". Mekanism's listener holds its owner weakly so a neighbour chunk's listener does not pin it. For a per-level SavedData that concern mostly disappears, because the SavedData lives as long as the `ServerLevel` the cache already references.
- **Listener body (#11).** NeoForge forbids `getCapability()` in the listener and advises against level access. Mekanism queues the side and re-evaluates it on the next server tick. `FluidSegments` already has a `LevelTickEvent.Post` hook (`FluidSegments.onLevelTick`), which is where a deferred re-check could run. A redraw is a `setBlock`, which counts as level access, so it would happen in that tick, not in the listener. Each re-check must call `getCapability()` again to re-arm the cache, and a cache never queried after creation never notifies.
- **Chunk load and unload (#11).** Listeners fire for the target's chunk, not the pipe's. A pipe on a chunk border sees its listener fire when the neighbour chunk unloads, and `getCapability()` then returns `null`. Mekanism and IE both treat "neighbour not loaded" as "leave the side as it is" rather than "no handler". A pipe in an unloaded chunk gets no notification; a pipe whose own chunk reloads has to recompute its arms itself, on load or `onPlace`. The level-unload case is explicitly not invalidated.
- **No block update, either way (#11).** NeoForge does not turn `invalidateCapabilities` into a block update. Pipez, IE and Create rely on block updates alone, so the stale-arm case in #11 is the gap their code leaves open. Only Mekanism's cache-plus-tick pattern covers it.
- **Pipeworks' own capability is side-blind (#9, #11).** `PipeworksRegistries.registerCapabilities` returns `FluidSegments.handlerAt(pos)` for any `side`, so Pipeworks pipes and tanks expose `Capabilities.Fluid.BLOCK` on all faces. A capability-based arm check would also match neighbouring Pipeworks nodes, and a foreign cable would still see a handler on a side wrenched off in #9. By comparison, IE returns `null` for a disabled side and calls `invalidateCapabilities()` when it toggles. `FluidSegments.changed` already calls `level.invalidateCapabilities(pos)` for a pipe's own position.
- **Click conventions (#9).**
  - **Toggle click:** plain right-click in IE and MI; sneak-right-click in Pipez and in Mekanism's Configurator.
  - **Sneak with a wrench:** dismantles in Mekanism, AE2 and Create, and in MI on a pipe.
  - **Choosing the side:** every toggling mod uses the hit position on the arm's shape, falling back to the clicked face on the core. Pipez and MI make the core-click the way to **re-open** a closed side, since a closed arm has no shape to hit. IE instead outlines closed arms while the hammer is held.
- **Which wrench (#9).** `c:tools/wrench` is populated by Mekanism, Pipez, MI, Create and AE2, but not by IE's own data. Pipez, MI, Create and AE2 already treat any tagged item as their wrench on their own blocks. NeoForge's doc on the tag discourages using it to decide behaviour. NeoForge's 26.1 `ItemAbilities` were not checked for a wrench ability.
- **Closed-side visuals (#9).** All five mods with a manual disconnect draw a closed side exactly like an empty one: Mekanism, Pipez, IE, MI, and Create's encased pipe. None adds a cap or plug model. The only cue is IE's hammer-held selection outline. Of the surveyed mods, only Pipez keeps arms in blockstate, as Pipeworks does. It stores "disconnected" outside the blockstate, in an on-demand block entity, and sets the arm to `false`. Pipeworks would keep the per-side mask in `FluidSegments` instead, per #9.
